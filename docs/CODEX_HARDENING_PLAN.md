# sshm 健壮性与体验改进执行计划

本文档是一份可以直接交给 Codex 执行的仓库级修复任务说明。

## 目标

在不破坏现有用户配置、密码库和常用命令行为的前提下，完成 sshm 的安全加固、数据一致性修复、认证行为统一、交互体验改善和测试体系补齐。

完成后，软件应满足以下总体要求：

- 原生 SSH 连接不会跳过主机密钥验证。
- 主机别名修改、重复别名、删除主机等操作不会导致密码错绑或残留。
- `hosts.yaml` 与 `secrets.yaml` 在异常退出、磁盘写入失败和并发运行时不会被截断或静默覆盖。
- `connect`、`ping`、`exec` 使用一致的认证策略、密钥路径和错误语义。
- 交互模式会展示命令错误，不会因普通操作失败直接退出。
- Windows 密码输入不回显，交互式输入支持 UTF-8。
- Release 在测试通过后才允许构建和发布。
- 现有 v1 配置与密码库可自动、无损迁移。

## Codex 执行要求

执行本计划时必须遵守以下约束：

1. 先阅读完整仓库，再开始修改。
2. 不删除或重建现有 `hosts.yaml`、`secrets.yaml`、导入密钥或用户 `known_hosts`。
3. 所有格式迁移必须向后兼容，并提供自动化迁移测试。
4. 不在日志、测试输出、提交内容或文档中输出真实密码、主密码、私钥或访问令牌。
5. 不使用 `os.Exit` 处理库层或交互模式中的普通错误。
6. 每个阶段完成后运行该阶段要求的测试；测试失败时继续修复，不得跳过。
7. 保持修改聚焦，避免无关重构。
8. 使用非交互式 Git 命令；不得使用 `git reset --hard` 或覆盖用户改动。
9. 完成所有阶段后再提交、推送和发布；除非用户明确指定版本号，否则使用下一个补丁版本。
10. GitHub PAT 撤销属于外部账户操作。Codex 应清理本地 remote URL，但不得声称已撤销无法验证的令牌。

## 阶段一：安全的主机密钥验证

### 当前问题

`internal/sshx/native.go` 在 `known_hosts` 不存在或不可读时会接受任意主机密钥。该行为可能遭受中间人攻击，且当前警告所称的 `accept-new` 并未真正保存密钥。

### 实施要求

1. 为原生 SSH 实现严格的 known-hosts 策略：
   - 已知且匹配：允许连接。
   - 已知但不匹配：拒绝连接，展示明确的主机密钥变更错误。
   - 首次连接且运行于交互终端：展示主机、算法和 SHA256 指纹，询问用户确认。
   - 用户确认后，以兼容 OpenSSH 的格式原子追加到 `~/.ssh/known_hosts`。
   - 首次连接且运行于非交互环境：默认拒绝，不得自动接受。
2. 创建 `~/.ssh` 和 `known_hosts` 时使用合理权限：
   - `~/.ssh`: `0700`
   - `known_hosts`: `0600`
3. 主机名匹配必须正确处理非 22 端口，使用 `[host]:port` 格式。
4. 不要静默绕过损坏、不可读或权限错误的 `known_hosts`。
5. 将主机密钥验证逻辑抽成可测试组件，避免测试依赖真实网络。

### 验收测试

- 已知主机密钥匹配时通过。
- 已知主机密钥变化时拒绝。
- 首次连接确认后写入正确条目。
- 首次连接拒绝后不修改文件。
- 非交互首次连接拒绝。
- 不可读或损坏的 `known_hosts` 返回可理解错误。

## 阶段二：稳定主机 ID 与无损数据迁移

### 当前问题

密码库使用主机别名作为存储键。重复别名会覆盖密码，主机改名会导致密码引用失效，搜索结果中的临时 ID 也可能指向错误主机。

### 设计要求

1. 为 `config.Host` 增加不可变稳定 ID，例如 UUID：

```yaml
version: 2
hosts:
  - id: "..."
    alias: "prod"
```

2. `PasswordRef` 改为引用稳定 ID，不再引用别名。
3. 保留用户可见的列表序号，但不得把序号当持久标识。
4. 所有新增主机必须：
   - 生成稳定 ID。
   - 拒绝重复别名。
5. 编辑主机别名时：
   - 稳定 ID 不变。
   - 密码引用不变。
   - 拒绝改成已有别名。
6. 删除主机时：
   - 提示是否同时删除保存的密码与由 sshm 管理的密钥。
   - 默认删除对应密码，避免秘密残留。
   - 不得自动删除 sshm 管理目录之外的密钥。
7. 搜索结果必须保留并展示完整主机列表中的真实序号，或引导使用别名连接，不能展示会指向其他主机的临时序号。

### v1 到 v2 迁移要求

1. 加载 v1 `hosts.yaml` 时，为每台主机生成稳定 ID。
2. 如果旧主机存在 `password_ref`：
   - 使用旧引用读取密码。
   - 以新稳定 ID 写入同一密码。
   - 更新 `password_ref`。
   - 确认新密码可读取后再删除旧条目。
3. 迁移必须具备事务性：
   - 任一步失败时，不覆盖原始 `hosts.yaml` 或 `secrets.yaml`。
   - 迁移前创建带时间戳或固定 `.bak` 的备份。
4. 同一个旧密码引用被多台主机使用时，不得误删仍被使用的旧条目。
5. 迁移需要用户输入主密码时，应先解释迁移目的；取消迁移不得损坏数据。

### 验收测试

- v1 无密码配置迁移到 v2。
- v1 有密码配置迁移后密码仍可读取。
- 改名后保存密码仍可用。
- 重复别名添加和编辑均被拒绝。
- 删除主机后对应秘密按用户选择正确处理。
- 任一步模拟写入失败时原文件保持不变。
- 搜索结果 ID 不会连接到错误主机。

## 阶段三：原子写入、备份与并发保护

### 当前问题

`hosts.yaml` 和 `secrets.yaml` 使用 `os.WriteFile` 直接覆盖。异常退出、磁盘写满或多个 sshm 进程同时写入时，可能产生截断文件或丢失更新。

### 实施要求

1. 新增共享的安全文件写入辅助函数：
   - 在目标目录创建临时文件。
   - 设置目标权限。
   - 写入完整内容。
   - 调用文件 `Sync`。
   - 原子重命名到目标路径。
   - 尽可能同步目录。
   - 错误时清理临时文件并保留原文件。
2. `hosts.yaml` 与 `secrets.yaml` 写入均使用该辅助函数。
3. 写入前保留最近一份有效备份，例如：
   - `hosts.yaml.bak`
   - `secrets.yaml.bak`
4. 加入跨进程文件锁，确保读改写操作不会互相覆盖。
5. 锁应覆盖完整事务，而不仅是最终写文件步骤。
6. 加载主文件失败且备份有效时：
   - 明确告知用户。
   - 提供恢复建议。
   - 不得静默使用备份后覆盖主文件。

### 验收测试

- 正常写入成功且权限正确。
- 模拟中途写入失败时原文件不变。
- 两个并发写入不会产生截断 YAML。
- 备份包含上一次有效内容。
- 临时文件在失败后被清理。

## 阶段四：统一认证与 SSH 执行引擎

### 当前问题

`connect`、`ping` 和 `exec` 使用不同代码路径，认证策略、密钥路径、回退行为和额外 SSH 参数不一致。

### 实施要求

1. 定义统一的认证计划或执行器，供以下操作共享：
   - 交互连接
   - ping
   - 单机 exec
   - 分组 exec
   - 全部主机 exec
2. 认证策略语义必须一致：
   - `key`: 仅使用配置的密钥，失败后不回退密码。
   - `password`: 仅使用保存密码或明确询问密码。
   - `ask`: 每次使用系统 SSH 或明确询问，不读取保存密码。
   - `system`: 完全交给系统 SSH 默认行为。
   - `auto`: 按明确且可预测的顺序尝试，并在输出中说明回退。
3. 使用配置密钥时，`ping` 与 `exec` 必须传递：
   - `-i <IdentityFile>`
   - `IdentitiesOnly=yes`
4. 原生密码连接无法支持的 OpenSSH 参数必须：
   - 明确回退到系统 SSH；或
   - 明确报错说明不支持。
   - 不得静默忽略 `-L`、`-R`、`-J` 等参数。
5. 底层执行函数返回结构化错误和退出码，不调用 `os.Exit`。
6. 为网络操作支持 `context.Context` 和可配置超时。
7. 修复交互连接中错误变量遮蔽导致输出 `<nil>` 的问题。

### 批量执行要求

1. 分组不存在或没有匹配主机时返回明确提示。
2. 批量执行结束后展示汇总：
   - 成功数量
   - 失败数量
   - 每台失败主机及原因
3. 任意主机失败时命令整体返回非零状态。
4. 支持合理的并发上限，默认值应保守。
5. 支持单主机超时，超时不阻塞其他主机。
6. 输出必须标记主机来源，避免并发输出混杂。

### 验收测试

- 每种认证策略在 connect/ping/exec 中行为一致。
- 配置密钥在 ping/exec 中被实际使用。
- `auto` 回退路径可预测且有测试。
- 额外 SSH 参数不会被静默丢弃。
- 普通连接失败不会退出交互模式。
- 批量执行部分失败时返回非零状态并展示汇总。

## 阶段五：交互模式与跨平台输入体验

### 当前问题

交互模式忽略命令错误；行编辑器只接受 ASCII；Windows 密码输入会回显且不支持空格；主密码在同一会话中被反复询问。

### 实施要求

1. 统一交互命令分发：
   - 每个命令返回 `error`。
   - 交互循环捕获并展示错误。
   - 错误后继续显示提示符。
2. 启动交互模式时，配置加载失败必须展示错误并安全退出，不能忽略错误或空指针崩溃。
3. 移除库层和命令辅助函数中的 `os.Exit`；只允许 `main` 根据最终错误决定退出码。
4. 行编辑器支持完整 UTF-8 输入：
   - 中文备注、分组、标签和命令可正常输入。
   - 光标移动、退格和删除按 rune 或 grapheme 正确工作。
   - CJK 宽字符光标位置正确。
5. Windows 使用 `term.ReadPassword` 或等价的不回显方案，不使用 `fmt.Scanln`。
6. 增加会话级密码库解锁：
   - 同一交互会话内只需解锁一次。
   - 支持显式 `lock` 命令。
   - 可选支持空闲超时自动锁定。
   - 主密码不得写入磁盘、日志或历史。
7. 首次创建密码库时：
   - 禁止空主密码，或要求显式确认风险。
   - 要求输入两次主密码确认。
   - 清楚说明主密码无法恢复。
8. `copy` 命令名实，应真正写入系统剪贴板；若不实现，应改名或明确输出“连接命令”。

### 验收测试

- 交互命令失败后显示错误并继续运行。
- 配置损坏时不崩溃。
- 中文输入、移动、删除正常。
- Windows 密码输入不回显并支持空格。
- 会话内重复操作不会反复询问主密码。
- `lock` 后再次访问秘密会重新询问主密码。

## 阶段六：配置导入导出、密钥与文档修正

### 实施要求

1. SSH config 导入：
   - 使用更可靠的解析器或完善当前解析逻辑。
   - 正确处理一个 `Host` 行包含多个别名。
   - 跳过通配符和无效条目。
   - 导入前调用主机验证逻辑。
   - 正确展开 `~` 路径。
2. SSH config 导出：
   - 创建目标父目录。
   - 使用原子写入。
   - 对包含空格的路径正确引用。
3. 密钥管理：
   - 检查 `Chmod` 错误。
   - 导入密钥时避免静默覆盖已有文件。
   - 验证导入内容确实是可解析的私钥。
   - 主机删除和改名时正确处理 sshm 管理的密钥。
4. 修正文档：
   - README 仓库地址改为实际仓库地址。
   - 不宣称尚未实现的自动补全。
   - 增加配置目录、备份恢复、主密码安全和 known-hosts 行为说明。
   - 添加真实 `LICENSE` 文件，或移除无效许可证链接。
5. 支持 `NO_COLOR` 的同时，在非 TTY 输出中默认禁用颜色。

## 阶段七：测试、CI 与发布门禁

### 测试要求

至少为以下模块增加测试：

- `internal/config`
  - 加载、验证、重复别名、稳定 ID、v1 到 v2 迁移、原子写入。
- `internal/secret`
  - 保留现有测试，增加重命名、迁移、并发写与备份测试。
- `internal/sshx`
  - known-hosts 策略、认证计划、命令参数构造、错误与退出码。
- `internal/command`
  - 交互错误展示、搜索结果 ID、批量执行汇总。
- `internal/ui`
  - UTF-8 行编辑、CJK 光标、历史与转义序列。

测试不得连接真实服务器，也不得读取或修改用户真实配置。使用 `t.TempDir()`、依赖注入和假执行器。

### CI 要求

新增独立 CI workflow，在 push 和 pull request 时运行：

```bash
go test ./...
go test -race ./...
go vet ./...
go test -cover ./...
```

发布 workflow 必须：

1. 使用与 `go.mod` 一致的 Go 版本。
2. 在构建前运行测试和 `go vet`。
3. 测试失败时不得创建 Release。
4. 所有目标平台构建失败时不得创建 Release。
5. 校验预期的六个平台制品全部存在，不能使用 `if-no-files-found: ignore` 掩盖缺失。
6. 保留版本注入并验证每个构建产物的版本信息。

### 最终验证矩阵

```bash
gofmt -w <所有修改的 Go 文件>
git diff --check
go test ./...
go test -race ./...
go vet ./...
go test -cover ./...

GOOS=linux GOARCH=amd64 go build ./...
GOOS=linux GOARCH=arm64 go build ./...
GOOS=darwin GOARCH=amd64 go build ./...
GOOS=darwin GOARCH=arm64 go build ./...
GOOS=windows GOARCH=amd64 go build ./...
GOOS=windows GOARCH=arm64 go build ./...
```

还需完成以下手工验证：

- 使用临时配置创建主机、保存密码、重启、连接。
- 修改主机别名后确认密码仍可读取。
- 重复别名被拒绝。
- 错误主密码不会修改密码库。
- 损坏配置不会被静默覆盖。
- 首次主机密钥确认后写入临时 `known_hosts`。
- 主机密钥变化后连接被拒绝。
- 交互模式错误后继续运行。
- 中文备注、分组和标签输入正常。
- 批量执行部分失败时返回失败并展示汇总。

## 建议提交顺序

为了降低回归风险，按以下顺序创建独立提交：

1. `security: enforce SSH host key verification`
2. `fix: add stable host IDs and migrate password references`
3. `fix: make config and secret writes atomic`
4. `refactor: unify SSH authentication and execution`
5. `fix: surface interactive errors and remove internal exits`
6. `feat: improve Unicode and password input`
7. `test: cover config SSH and interactive workflows`
8. `ci: gate releases on tests and complete artifacts`
9. `docs: update installation security and recovery guidance`

每个提交都必须独立通过：

```bash
go test ./...
go vet ./...
git diff --check HEAD^
```

## 完成定义

只有全部满足以下条件时，任务才算完成：

- 所有 P0/P1 问题已修复。
- v1 配置和密码库迁移测试通过。
- 所有自动化测试、race 检测、vet 和六平台编译通过。
- 工作区无意外文件和未提交修改。
- remote URL 不包含凭据。
- README 与实际行为一致。
- CI 和 Release workflow 具备测试门禁。
- 创建补丁版本 tag 并推送。
- GitHub Release 成功，六个平台制品和校验文件齐全。
- 下载至少一个正式发布制品，验证 `sshm --version` 和基本启动行为。

## 最终汇报格式

Codex 完成后应向用户汇报：

1. 修复的高风险问题和行为变化。
2. 配置迁移与兼容性说明。
3. 新增测试和验证结果。
4. 提交 SHA、版本号、Release 链接。
5. 仍需用户手动完成的事项，例如撤销旧 GitHub PAT。
